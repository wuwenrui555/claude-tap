# claude-tap v0.1.3: surface message-content fields

## Context

Downstream consumers (ccmux-backend-2, eventually replacing
ccmux-backend's transcript-polling code) want to reconstruct a
session's per-message stream from claude-tap events alone, with no
dependence on `~/.claude/projects/*.jsonl` transcript files.

claude-tap's hook stdin already carries everything those consumers
need — but our `extract_payload` deliberately drops several
fields. This release surfaces them. The change is additive only:
no consumer of v0.1.x events is affected; v0.1.3 events simply
carry extra optional fields.

The brainstorm spec
[`docs/superpowers/specs/2026-05-08-claude-tap-design.md`](2026-05-08-claude-tap-design.md)
is unchanged in spirit — claude-tap remains a faithful
hook-stream forwarder. v0.1.3 just stops dropping fields that are
already in stdin.

## Goals

- Surface `last_assistant_message` on `Stop` events. This is the
  text claude said at the end of the turn; without it, downstream
  consumers cannot rebuild assistant message replies from hook
  events alone.
- Surface `tool_use_id` on `PreToolUse` and `PostToolUse`. Pairs a
  tool call with its result across the two hook fires.
- Surface `duration_ms` on `PostToolUse`. Useful for displaying
  how long a tool ran.
- Acknowledge `agent_id` / `agent_type` (subagent fields, observed
  via drift.log on 2026-05-09) by adding them to the optional set
  for `PreToolUse` / `PostToolUse`. We don't need to surface them
  in the payload for v0.1.3 — just stop drift-warning about them.

## Non-goals

- **No streaming / partial assistant text.** Hooks fire at turn
  boundaries; mid-stream text never reaches a hook. If a consumer
  wants typewriter-style display, it still needs to tail
  `transcript_path`. claude-tap is not the right layer for that.
- **No `thinking` blocks.** Claude's reasoning blocks are written
  to the transcript but never reach a hook. Consumers that need
  thinking text continue reading the transcript file.
- **No image extraction.** `PostToolUse.tool_response` already
  carries image data when present (e.g., screenshot tools); the
  payload structure is unchanged. Consumers parse it themselves.
- **No new event types.** The 8 hooks remain the 8 hooks.

## Payload changes

### `Stop`

Before:

```json
"payload": {}
```

After:

```json
"payload": {
  "last_assistant_message": "Here's what I changed in foo.py..."
}
```

Empty string when claude's stdin omits the field (older Claude
Code versions or turns where the assistant produced no final text
block, e.g. ended on a tool call).

### `PreToolUse`

Before:

```json
"payload": {
  "tool_name": "Bash",
  "tool_input": {"command": "ls"}
}
```

After:

```json
"payload": {
  "tool_name": "Bash",
  "tool_input": {"command": "ls"},
  "tool_use_id": "toolu_01abc..."
}
```

Empty string when stdin omits it (defensive default).

### `PostToolUse`

Before:

```json
"payload": {
  "tool_name": "Bash",
  "tool_input": {"command": "ls"},
  "tool_response": {"stdout": "foo\n", "stderr": "", ...}
}
```

After:

```json
"payload": {
  "tool_name": "Bash",
  "tool_input": {"command": "ls"},
  "tool_response": {"stdout": "foo\n", "stderr": "", ...},
  "tool_use_id": "toolu_01abc...",
  "duration_ms": 17
}
```

`duration_ms` is `0` when stdin omits it.

### Other events

`SessionStart`, `UserPromptSubmit`, `Notification`, `SessionEnd`,
`PermissionRequest` — payloads unchanged.

## drift.py adjustments

Move from `optional` → `required` for `_EXPECTED`:

- `Stop`: add `last_assistant_message` to required (the field is
  empirically always present on real Claude Code 2.1.x; if a
  consumer-facing minimum-version concern arises, demote later).
- `PreToolUse`, `PostToolUse`: add `tool_use_id` to required.
- `PostToolUse`: add `duration_ms` to required.

Add to `_TOOL_OPTIONAL`:

- `agent_id`, `agent_type` — observed in drift.log on 2026-05-09
  for subagent-spawned tools. Optional because pre-subagent
  tools and pre-Claude-Code-X versions don't emit them.

**Layered defense:** marking a field `required` in drift.py and
giving it a defensive default in `extract_payload` is intentional,
not contradictory. Drift logs an alert if a future Claude Code
release drops the field; meanwhile the payload still produces a
valid event (with `""` / `0`) so no consumer crashes. Without the
drift alert we'd silently degrade; without the default we'd
crash. We want both.

## Backwards compatibility

Pure-additive change. Consumers reading v0.1.0–v0.1.2 events get
the same fields they always got; v0.1.3 events have extra keys
they can ignore. No event_type renamed. No payload field
removed. No schema_version bump needed (we use `schema_version: 1`
for the envelope, not the payload — payload schema is per-event
and additively extensible by design).

## Testing

1. **Unit / extract_payload table-driven tests** — for each
   modified event type, feed a synthetic stdin dict with the new
   fields and assert the payload contains them.
2. **Drift-detection unit tests** — feed stdin with all required
   fields present; assert no drift is logged. Then feed stdin
   without the new required fields (simulating older Claude
   Code); assert drift IS logged.
3. **Round-trip integration** — write a synthetic event through
   `run()` with stdin populated, parse the line back from the
   `events.jsonl`, confirm the payload matches expectations.
4. **Live smoke test (manual)** — run a real claude session
   through the wrapper, trigger one tool call (Bash), one
   permission flow (AskUserQuestion), one plan review
   (ExitPlanMode), and end the turn. Inspect the resulting
   `events.jsonl` to confirm the new fields appear with non-empty
   values where expected.

## Release

Standard git-flow:

- bugfix branch off dev for the field additions
- merge to dev with `--no-ff`
- release/v0.1.3 from dev: bump version (pyproject.toml,
  `_version.py`, `tests/test_skeleton.py`) + CHANGELOG entry
- merge release into main, tag v0.1.3, merge back into dev
- pre-push checks (ruff / format / pyright / pytest) all green
- push origin main dev --tags

## Open questions for implementation phase

- **Empty `last_assistant_message` semantics**: when the assistant
  ends a turn on a tool call without text, is the field absent or
  empty? Implementation should check stdin behavior and document.
- **`duration_ms` units**: assumed milliseconds based on the field
  name; verify against real captures.
